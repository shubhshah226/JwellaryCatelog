Jewelry Catalog Platform
Backend API Specification
Version 1.0  |  2026-09-03Base URL (proposed): https://{host}/api/v1Auth: Bearer JWT (except public + OTP endpoints)
1. Document Purpose
This document defines the database tables, REST endpoints, request payloads, and response contracts required to replace the current json-server mock API with a real backend. It also covers business rules for vendor login eligibility, Phase-1 limited storefront options, and the new cart-style combined lead flow.
1.1 Scope (Phase 1)
Admin: dashboard stats, vendors CRUD, users CRUD, roles CRUD
Vendor: dashboard, catalogs, products (multi-image), leads (combined cart), profile (email/phone only), My Website (limited options)
Public storefront: home, products, short catalog share links
Customer OTP verify + interest cart → single lead entry
Auth: admin + vendor login with inactive / plan-expired blocking
1.2 Out of Scope (Later)
Dynamic custom HTML/CSS sections on vendor websites
Advanced section placement builder
Payment / billing gateway for plans
Real SMS OTP provider (Phase 1 can use mock / configurable OTP)
2. Conventions
JSON request/response; Content-Type: application/json
IDs are integers (BIGINT) unless noted
Timestamps: ISO-8601 UTC (e.g. 2026-09-03T10:00:00Z)
Money: integer/decimal INR (price stored as decimal(12,2))
Images: upload via multipart OR send image URLs after upload service; avoid huge base64 in production
Standard error shape: { "success": false, "error": { "code": "STRING", "message": "..." } }
Standard success shape: { "success": true, "data": ... } or { "success": true, "data": ..., "meta": {...} }

3. Authentication & Vendor Login Rules
Login uses username + password. On success, API returns JWT access token and user profile. For role=vendor, backend MUST enforce eligibility before issuing a token.
3.1 Vendor Login Eligibility
If linked vendor.status = 'inactive' → reject login with VENDOR_INACTIVE
If vendor.subscription_type = 'expiry' OR subscription_end_date < today → reject with PLAN_EXPIRED
If vendor.status = 'trial' and trial_end_date < today → treat as PLAN_EXPIRED (or convert status server-side)
Admin users are never blocked by vendor plan rules
Public storefront may still show a 'unavailable' page when vendor is inactive; login to dashboard is blocked

5. Lead Flow Change (Add-to-Cart Style)
Current (to replace): each product interest creates a separate enquiry row.
New flow:
Customer browses products on public store / shared catalog
On product click → OTP verify once per store session
After verify: view full details + extra images; button becomes Add to Interest Cart
Cart persists for session (client or server); show cart badge with count
Cart page / drawer: list selected products, remove item, optional note
Submit Interest → ONE POST creates lead + lead_items
Vendor Leads page: one entry showing customer + N products; status updates apply to whole lead
Optional: vendor can mark individual items as discussed later (not required Phase 1)
6. API Endpoints
6.1 Auth
POST /auth/login
Login for admin or vendor.
Auth: Public
Request body / params:
{  "username": "vendor",  "password": "vendor"}
Success response:
{  "success": true,  "data": {    "token": "<JWT>",    "user": {      "id": 2,      "name": "Shubh Jewellers",      "firstName": "Shubh",      "lastName": "Jewellers",      "username": "vendor",      "email": "vendor@shubhjewellers.com",      "role": "vendor",      "vendorId": 1    }  }}
Notes:
On vendor inactive: HTTP 403, code VENDOR_INACTIVE
On plan/subscription expired: HTTP 403, code PLAN_EXPIRED
JWT claims: sub=userId, role, vendorId?
POST /auth/logout
Invalidate token/session (optional if JWT-only).
Auth: Bearer
Success response:
{ "success": true }
GET /auth/me
Return current user from token.
Auth: Bearer
Success response:
{ "success": true, "data": { "id": 2, "role": "vendor", "vendorId": 1, ... } }

8. Implementation Notes for Backend Team
Always scope vendor APIs by JWT vendorId — never trust client-supplied vendorId for writes
On admin vendor create: generate store_code, create default storefront row + banners empty
Public store isAvailable only when vendors.status = active
Login eligibility is separate from public isAvailable (both should check inactive/expiry)
Prefer image upload service returning URLs over storing base64 in DB
Phase 1 storefront API must not accept customSections HTML/CSS
Migrate existing enquiries → leads + lead_items (1 product each) if needed
Short catalog links stored in catalog_shares; public route uses short_code
CORS allow frontend origin; rate-limit OTP and login
